# 00 — 产品总览

## 1. 背景

组织内部的数据分散在多种数据库引擎中（PostgreSQL、MySQL、Oracle、Redshift、ClickHouse、MongoDB 等）。当前数据访问面临以下痛点：

1. **访问入口割裂**：每个人使用各自的数据库客户端（DBeaver、DataGrip、命令行等），连接凭据四处散落，难以集中管理。
2. **权限粒度粗**：通常只能到「数据库账号」级别，无法做到表级、列级的细粒度授权；DBA 通过手工 grant/revert 管理，易遗漏、易失控。
3. **缺乏审计**：谁在什么时间查询/导出了什么数据、尤其是敏感数据，缺乏完整、不可篡改的记录，无法满足合规要求。
4. **敏感数据暴露风险**：身份证号、手机号、银行卡号等字段若授权不当会在查询结果与导出文件中暴露。v1 通过数据库授权（GRANT）与全量审计控制访问；应用层动态脱敏延后到 v2。
5. **身份不统一**：组织已有企业身份系统（LDAP/AD、OIDC IdP），但数据库账号与人员身份脱节，离职/调岗后账号回收滞后。

## 2. 愿景

构建一个 **集中式、受控、可审计** 的数据库访问工作台。用户登录后，在统一界面中选择被授权的数据库，编写 SQL（支持自动补全）进行查询，或发起数据导出任务；每一次访问都经过精确的权限校验，并写入不可篡改的审计日志。

## 3. 目标用户

| 角色 | 典型身份 | 核心诉求 |
|---|---|---|
| **数据分析师/业务方** | Analyst、运营、产品 | 自助查询数据、导出报表，不需要直接接触数据库 |
| **开发工程师** | 后端/前端开发 | 联调排查时查询线/测试库数据，查看 schema |
| **DBA / 数据平台工程师** | DBA | 管理实例/连接/数据源、元数据同步、排查问题（**不**做项目 IAM） |
| **安全管理员** | Security、合规 | 审查审计日志、配置环境策略与访问护栏、监督授权合规 |
| **系统管理员** | 平台负责人 | 配置 IdP 集成、用户/组管理、环境与项目管理 |

> 关键设计原则：**职责分离（SoD）**。安全管理员与 DBA 角色分离：DBA 管理连接与实例，安全管理员监督审计与访问策略，互不越权。

## 4. 核心使用场景

### 场景 A：自助 SQL 查询（最高频）
1. 用户通过 SSO 登录系统。
2. 在工作台选择一个数据库（系统仅展示其有访问权的数据库）。
3. 在 SQL 编辑器中编写查询，编辑器基于该库的 schema 提供 **表/列/函数的自动补全**。
4. 执行查询，结果分页展示（受行数/超时上限保护）。
5. 查询语句被记录到该用户的查询历史，并写入审计日志。

### 场景 B：数据导出
1. 用户选择数据库，填写导出 SQL 与格式（CSV / JSON；XLSX / SQL 格式延后到 v2）。
2. 若数据量小：同步导出，立即下载带密码的压缩包。
3. 若数据量大：提交异步导出任务，任务完成后在通知中心下载；任务产物有保留期（默认 24h）。
4. 导出行为完整记入审计。

### 场景 C：临时访问敏感数据（JIT）—— v2
> 列级动态脱敏与 JIT 临时去脱敏均延后到 v2（见 §5.3）。v1 期间，敏感数据的可见性由数据库授权决定，临时放行通过 DBA 调整授权 + 全量审计实现。

### 场景 D：合规审计回溯
1. 安全管理员在审计中心按「操作类型=导出、时间=上月、用户=某分析师」筛选。
2. 查看每一条审计记录的：操作人、IP、UA、时间、目标库表、SQL 摘要、状态。
3. 一键导出审计结果用于合规报告。

## 5. 范围与边界

### 5.1 产品范围（完整交付）

| 能力域 | 说明 |
|---|---|
| 资源管理 | Instance / Database / Schema / Table / View / Column 的发现、同步与展示 |
| SQL 查询工作台 | 多语句执行、自动补全（LSP）、结果分页、查询历史、EXPLAIN |
| 数据导出 | 同步 + 异步导出，CSV / JSON（v1），密码压缩包 |
| 权限体系 | RBAC + 项目隔离 + 库/表级结构化授权 + 环境护栏 |
| 认证集成 | 本地账号/密码、LDAP、OIDC、SSO、JIT provisioning、组映射、MFA |
| 审计日志 | 全量关键操作审计、不可篡改、可查询导出 |
| SQL 收藏与分享 | 个人收藏夹、基于 Worksheet 可见性的安全分享 |
| 数据库引擎支持 | **当前版本仅实现 PostgreSQL**（未来按需扩展，见 §5.2） |

### 5.2 数据库引擎支持策略

> **当前版本仅实现 PostgreSQL，核心代码原生实现，不预设多引擎插件抽象。**

- 连接、查询、导出、权限、审计、自动补全均针对 PostgreSQL 实现。
- 未来若确需接入其他引擎（MySQL、Oracle 等），届时再抽取驱动/解析器抽象（届时拥有第二个数据点，抽象更准确）——**不为尚不存在的引擎提前支付抽象与维护成本**。

### 5.3 范围边界

**v1 产品定位边界（不做）：**
- 不直接作为数据库的高可用/备份/迁移工具。
- 不替代业务系统的 OLTP 入口（仅面向人/BI 的查询与导出）。
- 不实现数据库账号的自主开通与自助密码修改（由 DBA 管理）。

**不在 v1 范围、计划 v2 或未来引入：** 见 [18-roadmap.md](./18-roadmap.md)。要点：列级脱敏/谓词列保护、JIT、查询成本护栏、多引擎、Service Account/PAT、XLSX/SQL 导出、分享增强、自定义角色；更远的数据库变更管理、行级权限（RLS）、多租户。v1 期间敏感数据保护依赖组织现有数据库授权（GRANT）+ 全量审计。

## 6. 核心设计原则

1. **默认最小权限（Default Deny）**：任何未被显式授权的资源，默认不可访问。
2. **职责分离（SoD）**：DBA 管理连接与实例，不掌握平台审计与访问策略；安全管理员监督审计与策略，不掌握连接凭据。
3. **全程可审计（Audit by Default）**：关键操作通过注解声明，由拦截器统一记录，业务代码无法绕过。
4. **敏感数据由数据库授权控制**：v1 不做应用层脱敏；敏感列的可见性由数据库授权（GRANT）决定，平台全程审计访问行为。应用层动态脱敏延后到 v2。
5. **以 Project 做团队隔离（Team Isolation）**：每个产品团队一个 Project，库/成员/权限在 Project 内自治；跨 Project 默认拒绝，团队间数据互不可见。
6. **聚焦 PostgreSQL**：当前版本只面向 PostgreSQL，核心逻辑原生实现；不为多引擎提前抽象（见 §5.2）。

## 7. 成功指标（参考）

| 指标 | 目标 |
|---|---|
| 数据库引擎 | **PostgreSQL（v1）** |
| 权限最细粒度 | 表/库级（结构化授权 + 环境条件） |
| 审计覆盖率 | 所有关键操作 100% 记录，无绕过路径 |
| 单库 schema 同步延迟 | 自动同步周期内（≤ 15 min），手动触发可即时刷新 |
| 查询自动补全首字符响应 | P95 ≤ 200ms |
| 导出能力 | 单任务支持百万级行导出（异步） |

## 8. 术语表

| 术语 | 定义 |
|---|---|
| **Instance（实例）** | 一个物理数据库连接（host:port + 引擎类型 + 连接凭据）；**归属且仅归属一个 Project**，由该项目团队（projectOwner/projectDBA）管理 |
| **DataSource（数据源）** | Instance 下的连接配置，分 ADMIN（管理连接，用于同步）与 READ_ONLY（只读连接，用于查询） |
| **Database（数据库）** | Instance 内的逻辑库；**项目归属由其 Instance 决定**（实例在哪个项目，库就在哪个项目） |
| **Catalog（目录）** | 数据库的 schema 元数据（表/列/视图等） |
| **Project（项目）** | **产品团队的逻辑隔离边界**：每个团队在自己的 Project 内管理数据库、成员与权限；跨 Project 默认隔离 |
| **Environment（环境）** | 一等策略维度（dev/test/stage/prod）：实例必须标注、库可继承/覆盖；驱动访问控制、查询/导出护栏（按环境差异化） |
| **IAM Policy** | 权限绑定模型：`角色 × 成员 × (可选)结构化条件`（限定到环境/库/表） |
| **Audit Log（审计日志）** | 不可篡改的操作流水 |
| **Worksheet（保存的查询）** | SQL 的一等存储对象（标题、内容、可见性）；收藏与分享的载体 |
| **Favorite（收藏）** | 指向某 Worksheet 的个人私有快捷书签 |
| **LSP** | Language Server Protocol，SQL 自动补全的协议基础 |
