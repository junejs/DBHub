# 18 — 路线图（v2 及未来）

> 本文件是**不在 v1 范围、计划在 v2 或未来引入**的能力的唯一事实来源。v1 各文档仅在原处标注「不在 v1 范围」并指向本文件，不再重复 v2 设计细节。
>
> **产品永久边界**（不作为高可用/备份/迁移工具、不替代 OLTP 入口、不做自助 DB 账号）见 [00 §5.3](./00-overview.md)。

---

## 1. v2 范围（从 v1 延后）

> v1 以"实用优先"原则聚焦：集中式查询/导出 + RBAC/项目隔离 + 审计 + SSO（PostgreSQL 单引擎）。下列能力已从 v1 移出，按优先级与依赖排序。

### 1.1 列级动态脱敏 + 谓词列保护（QuerySpan）

- **为何不在 v1**：应用层结果掩码 + SQL 静态分析（提取谓词列/聚合/函数中的敏感列）安全攸关、实现重；解析器 bug = 数据泄露，且需覆盖子查询/CTE/UNION/VIEW/跨库 JOIN 等全部形态。v1 期间敏感列可见性由**数据库授权（GRANT）**决定，平台对全部访问做审计。
- **v2 方向**：
  - 列 Catalog 标注（`semantic_type`）+ 脱敏算法（range / full / md5 / inner_outer）+ 脱敏豁免（成员+列+时间窗）。
  - 谓词列保护：自建 QuerySpan 静态分析，**或**改走数据库原生列权限（更稳）。
  - 重新评估是否仍用"共享服务账号 + 应用层脱敏"模型，还是改为按角色的 DB 账号 + DB 原生列授权（届时可能调整 D2）。
- **涉及**：表 `data_classifications` / `semantic_types` / `masking_rules` / `masking_exemptions` / `column_annotations`；服务 `MaskingPolicyService` / `DatabaseCatalogService`；错误码 `PREDICATE_COLUMN_REJECTED`。

### 1.2 JIT 临时去脱敏访问

- **为何不在 v1**：主要用途是「临时去脱敏」，与 1.1 绑定；脱敏延后，JIT 一并延后。v1 临时放行由 DBA 在数据库侧调整授权 + 全量审计实现。
- **v2 方向**：申请 → 审批 → 限期生效 → 过期/手动失效 → 专项审计（可绑定到精确 SQL、可选导出）。引入通知类型 `jit_pending` / `jit_resolved`。
- **涉及**：表 `access_grants`；服务 `AccessGrantService`；`QueryResult.applied_access_grant` 字段。

### 1.3 查询成本护栏（EXPLAIN 估算）

- **为何不在 v1**：PostgreSQL `cost` 为任意单位（取决于 `seq_page_cost`/`random_page_cost` 等 GUC 与表统计），作为拦截阈值既会误杀正常查询也会漏放慢查询。v1 以**语句超时 + 行数/字节上限**保护业务库。
- **v2 方向**：若出现真实的"全表扫描拖垮库"事故，再评估更可靠的估计（如基于历史执行反馈的自适应阈值，或仅告警不拦截）。
- **涉及**：`environment_policies.query_cost_threshold`（v1 已从表中去掉）；错误码 `QUERY_COST_EXCEEDED`。

### 1.4 多数据库引擎

- **为何不在 v1**：v1 仅 PostgreSQL，核心代码原生实现。不为第二个引擎提前抽象（YAGNI）——从单一数据点臆想的抽象，等真到第二个引擎时大概率要返工。
- **v2 方向**：接入第二个引擎（MySQL/Oracle 等）时，从 PG 实现抽取 `Driver` / `Parser` / `Completion` 接口（届时有两个数据点，抽象更准），并引入能力矩阵（capability matrix）声明各引擎支持的功能、能力不足时优雅降级。
- **涉及**：`engine` 字段已为 `text`（可扩展，无需改表）；驱动/解析器/补全模块。

### 1.5 数据级条件表达式（CEL）

- **为何不做（除非未来有强需求）**：授权维度（环境/库/表）固定可枚举，v1 用结构化字段表达；CEL 暴露给非工程师（projectOwner/securityAdmin）易误配 = 越权。
- **未来方向**：仅当出现结构化字段无法表达的复杂条件（如动态时间窗、跨字段联动）时，再评估引入**受控的**表达式子集，仍以表单为主。

### 1.6 认证与身份增强

- **Service Account / API token**：自动化（BI 抽数、定时任务、CI）场景；与自然人账号分离，可绑定 IAM 角色。
- **通用 OAuth2 / 邮箱验证码登录**：v1 已有 OIDC + LDAP + 本地账号覆盖企业主路径。
- **SCIM 2.0 目录同步**：Entra ID / Okta 自动同步用户与组，配合离职自动回收。
- **密码策略增强 / 登录风险评分**。
- **涉及**：表 `access_tokens`；通知/审计相应事件。

### 1.7 数据导出增强

- **XLSX、SQL（`INSERT INTO ...`）导出格式**：v1 仅 CSV / JSON。
- **审批制批量导出**：审批通过后可走 ADMIN 连接、批量去脱敏导出（依赖 1.1）。
- **导出到外部对象存储**：存储抽象已预留 `export_archives(storage, location)`（D20），v1 为本地盘。
- **定时导出 / 订阅**（D6 未明确，按需）。

### 1.8 SQL 收藏与分享增强

- 文件夹 / 分组、置顶、备注（v1 收藏仅为星标）。
- `PROJECT_WRITE` 协作编辑、带 token 的分享链接（`LINK` 可见性，支持过期与吊销）。
- 评论、派生另存为模板、跨项目分享。
- **涉及**：表 `share_links`；`worksheets.visibility` 扩展；`FavoriteService` 扩展。

### 1.9 自定义角色

- **为何不在 v1**：8 个预置角色已覆盖绝大多数组织；自定义角色的 CRUD + 权限子集组合 + 审计成本不值得。
- **v2 方向**：若确有需求，支持基于权限子集创建自定义角色（预置角色不可改不可删）。

## 2. 未来延伸（更远，未定期）

| 方向 | 说明 | 架构预留 |
|---|---|---|
| **数据库变更管理** | schema 变更审批、迁移、版本管理、SQL Review、回滚 | 任务执行器与审批流抽象 |
| **行级权限（RLS）** | 同一表不同用户看不同行子集 | 优先走数据库原生（PG Row Security Policy / Oracle VPD / Snowflake Row Access Policy）；平台仅做策略管理与下发，不做 SQL 改写注入 |
| **多租户** | 若从单组织扩展到多组织 | 届时统一加 `tenant_id`（一次性迁移，v1 不背） |

## 3. v1 不做、且暂无 v2 计划

以下为产品定位决定的不做项（与路线图无关），详见 [00 §5.3](./00-overview.md)：

- 不作为数据库的高可用 / 备份 / 迁移工具。
- 不替代业务系统的 OLTP 入口（仅面向人 / BI 的查询与导出）。
- 不实现数据库账号的自主开通与自助密码修改（由 DBA 管理）。
- 不做敏感操作的 step-up 二次认证（v1 无审批流；D7）。
- 不做「查询结果」分享（只分享 SQL 文本；D10）。

## 4. v1 → v2 演进原则

1. **数据模型向前兼容**：v2 新增表/列，不改 v1 既有结构（见 [10 §5](./10-data-model.md)）。
2. **不提前抽象**：v2 的接口（Driver/Parser、脱敏引擎、JIT）在真正实现第二个实例时才从具体代码中抽取，不为想象中的需求预设框架。
3. **安全特性优先评估"数据库原生"**：脱敏、行级权限等，优先看能否下推给数据库（更可靠、绕不过），而非在应用层重造。
